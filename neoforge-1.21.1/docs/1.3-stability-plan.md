# FindMe 1.3 Stability Plan

FindMe 1.3 is the final stability-focused release. Do not expand major gameplay until the safety work below is complete.

Priority:

1. Do not lose official creatures.
2. Do not duplicate official creatures.
3. Keep state transitions understandable.
4. Keep compatibility isolated.
5. Improve UI and animation only after safety work is stable.

## Phase 1: Observability

- Mark official entities and temporary entities consistently.
- Add lifecycle logs through `FindMeDebugLogger.lifecycle`.
- Add read-only `CompanionIntegrityService`.
- Add `/findme doctor` and `/findme doctor verbose`.
- Run read-only integrity checks on player login and warn without modifying data.
- Doctor should report archive snapshot problems and orphan metadata/snapshots without attempting repair.

Doctor must not modify player data. It should report `OK`, `UNKNOWN`, `WARNING`, `CONFLICT`, and `CRITICAL`.

## Phase 2: Accident Prevention

- Verify a stored snapshot before an official world entity is removed.
- Vehicle storage must also persist a validated snapshot before removing the live vehicle entity or Sable sub-level.
- Add operation locks with timeout for deploy, store, switch, and recover.
- Add scoped transient-state cancellation.
- Clean expired temporary skill entities.
- Add local recovery points for dangerous operations.
- Create a safety backup before moving a registered creature into dead-record state; if the death is already real, continue recording the death but emit a lifecycle warning if the backup unexpectedly fails.

## Phase 3: Recovery

- Add rolling full-player backups at low-frequency safe points.
- Add backup list, validation, and restore preview.
- Add backup restore dry-run and confirm commands; bare restore previews only.
- Add vault restore dry-run and confirm commands; bare restore previews only.
- Add dry-run recovery commands for stored snapshots.
- Add commands to clear stale locks and remove confirmed temporary skill entities.
- Recovery, restore, lock-clear, and temporary-cleanup commands must create a safety backup first; if that backup cannot be created, cancel the mutation.
- Add conservative stored-snapshot recovery to storage or world, guarded by backup, lock, death-record, and loaded-entity checks.
- Create full backups before release/unbind and dead-record deletion from command or warehouse UI paths; if the backup cannot be created, cancel the destructive operation.
- Run integrity checks after recovery.

## Phase 4: Entry Consolidation

- Add `CompanionLifecycleFacade`.
- Route dangerous packet, command, binding, and lifecycle event entry points through the facade.
- First covered entries: companion summon, select-summon, recall, active collect, emergency rescue responder deployment, vehicle select-summon, vehicle recall, contract binding storage, travel/logout/death collection.
- Live official companion storage is now expected to pass through `CompanionLifecycleFacade.storeLiving`; direct `storeAndDiscard` use should remain inside the facade.
- Stored official companion deployment is now expected to pass through `CompanionLifecycleFacade.restoreStored*`; direct transfer calls should remain in the low-level transfer/storage implementation.
- Keep existing services for implementation; the facade validates, logs, locks, cancels transient state, and verifies results.

## Phase 5: Product Freeze

- Replace UI pages gradually.
- Disable or remove old UI entry points.
- Freeze compatibility scope.
- Run old-save, crash-shutdown, multiplayer, and third-party mod regression tests before release.
