# FindMe 1.3 Final Stability Audit

This is the current NeoForge 1.3 evidence map. It separates code-proven gates from manual regression items that still require an in-game run.

## Code-Proven Gates

Observability:

- Lifecycle logging is centralized through `FindMeDebugLogger.lifecycle`.
- `CompanionIntegrityService` is read-only and is used by `/findme doctor`, `/findme doctor verbose`, operator-targeted doctor, login checks, and post-recovery summaries.
- Doctor reports `OK`, `UNKNOWN`, `WARNING`, `CONFLICT`, and `CRITICAL`.
- Doctor checks records, teams, wheels, deployed state, stored snapshots, snapshot UUID mismatches, archive snapshots, backup checksums, orphan metadata, homes, operation locks, loaded world duplicates, and temporary skill performers.

Accident prevention:

- Official companion storage goes through `CompanionLifecycleFacade.storeLiving` and `CompanionStorageService.storeAndDiscard`.
- `CompanionStorageService` validates a stored snapshot before the official entity is discarded.
- Active registered entities that leave a level are snapshotted with lifecycle diagnostics instead of silently relying on the last old snapshot.
- Retreating official entities now acquire a `STORE` lock and verify `storeEntity` before the retreat removal.
- Vehicle storage writes and validates a snapshot before removing the live entity.
- Sable/Aeronautics storage writes a blueprint snapshot before removing sub-levels.
- Operation locks cover companion deploy/store, vehicle deploy/store, Sable deploy/store, and recovery-to-storage.
- Busy gates cover operation locks, pending storage effects, pending arrival effects, and pending vehicle summon effects.
- Cobblemon send-out has both Pokemon-level and player-level pending guards, preventing two different party entries from starting overlapping asynchronous send-outs for one player.
- Shared vehicle switches require positive retirement of FindMe-managed mount, vehicle, Sable, MachineMax, or Cobblemon sources before committing the destination; unmanaged external rides are explicitly exempt, and failed managed retirement triggers destination rollback plus a bounded source remount attempt.
- Expired temporary skill performers are cleaned by server tick and are ignored by Doctor's official-entity scan.
- Seat anchors are non-saving temporary entities and are discarded on orphan join.

Recovery:

- The 1.2 source path matches the original implementation (`player.getPersistentData().find_me`), with the per-save mirror used only as a fallback; existing world roots always win over legacy sources.
- Imported roots are decoded and normalized before commit, read back from world `SavedData`, fingerprint-verified, and only then marked with source/result/checksum metadata. Verification failure removes only the attempted world root and leaves legacy NBT available for retry.
- Destroyed-house positions and reconciliation revisions are persisted per world. Breaking an ownerless 1.2 house first backs up and collects every matching migrated resident, then commits the tombstone; offline or not-yet-migrated owners reconcile stale legacy home coordinates on their next load without affecting modern `homeHouseId` assignments.
- Old player data without a 1.3 safety schema marker creates a one-time `before_1_3_upgrade_login` backup on login before the marker is advanced.
- New full-player backups include a format version and checksum; Doctor and restore commands reject checksum-mismatched backups.
- Backup and vault restore have preview and confirm paths; bare restore commands preview only, so mutation requires `confirm`.
- Vault restore refuses empty, missing-id, UUID-mismatched, locked, or already-loaded vault snapshots before creating a restore backup.
- Backup restore confirmation refuses active player operation locks and clears transient state before applying the backup.
- Recovery and restore mutations resync companion, vehicle, death, and team client state after saving.
- Backup/vault restore confirmations create a backup first.
- Stored recovery has dry-run and conservative confirm paths.
- `recover-stored` refuses missing snapshots, invalid snapshots, UUID-mismatched snapshots, unknown records, dead records, active locks, loaded world entities, and pending storage animations.
- `drop-stale-stored` safely resolves stored+loaded conflicts by backing up first and removing only the stale stored snapshot while keeping the loaded world entity.
- Recovery, lock clear, temporary cleanup, release/unbind, dead-record deletion, vault clear, and sleep revive create safety backups before mutation.
- Release/unbind paths cancel transient state and write release lifecycle diagnostics after record removal.
- Lock recovery refuses owner mismatches, and Doctor no longer reports other players' operation locks as this player's unknown records.
- Recovery mutations run Doctor summaries afterward.

Entry consolidation:

- Companion summon, select-summon, recall, binding storage, lifecycle collection, emergency rescue deploy, vehicle select-summon, and vehicle recall enter through `CompanionLifecycleFacade`.
- Direct `CompanionManager.storeAndDiscard` is limited to the facade.
- Direct stored companion restore calls are limited to the facade plus documented home-return internals.
- Warehouse, team, home, skill, companion/vehicle wheel selection or edit, release, and vehicle commands use busy gates before mutating active records.

## Static Search Gates

Run before release:

```text
rg "CompanionManager\.storeAndDiscard\(" src/main/java/com/kuzhi/findme/server
rg "CompanionEntityTransferService\.restoreStoredEntity" src/main/java/com/kuzhi/findme/server
rg "\.discard\(" src/main/java/com/kuzhi/findme/server
rg "data\.remove\(|removeDeadAt\(|storedEntities\.remove\(" src/main/java/com/kuzhi/findme/server
rg "tryBegin\(|Operation\.DEPLOY|Operation\.STORE|Operation\.RECOVER" src/main/java/com/kuzhi/findme/server
```

Expected result: every hit is either a facade path, a validated snapshot path, a forced-backup destructive path, core data internals, or a documented temporary-entity exception.

## Runtime-Proven Gates

- [x] A copied real 1.2 world migrated through a dedicated NeoForge development server without modifying the original save. The imported world root contains one `player_nbt/imported` migration record with a 64-character source checksum, 14 mounts, 4 companions, 6 vehicles, 26 stored snapshots, 6 display names, 6 teams, 3 dead companions, and 6 backups.
- [x] Restarting and logging into the same migrated copy did not rerun or overwrite migration. The migration count stayed at one, `migratedAt` stayed at `1463`, all record counts stayed unchanged, and the authoritative `find_me_world_data.dat` SHA-256 stayed `CED3EA196B57A9650EF19A9EE83417C1CF4CE989F98EF492AC8C1FEEE2B071E0`.
- [x] Unordered legacy maps and sets now serialize deterministically before migration fingerprint verification. Verification remains strict and reports the first differing NBT path on failure; the legacy source remains retryable.

## Manual Gates Still Required

The following cannot be proven by static code inspection alone:

- Forced shutdown during pending storage and pending summon.
- Multiplayer simultaneous summon/store/switch.
- Sable/Aeronautics blueprint restore after game restart.
- Large modded flying creature NBT and preview fidelity after repeated wheel switching.
- Dedicated server run, not only integrated server.

Use `docs/release-checklist.md` as the manual runbook.
